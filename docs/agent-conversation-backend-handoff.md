# 对话式路线 Agent：后端改造边界

日期：2026-10-28。当前工作区是 Android 前端；`route-agent/` 是旧 Python 原型，
不是线上 Spring 服务。本次未修改或部署 `Viyangle/study_tour` 后端。

## 当前前端已完成

- 保存独立讨论对象：候选方案在新任务开始、追问、服务失败或页面恢复后不会被清空。
  未应用候选可作为下一轮规划基准，实际地图路线仍不变，应用时仍核对真实路线快照。
- `history` 使用真实用户消息和独立语义摘要，不再把带按钮提示、费用免责声明等整段 UI 文案当作记忆。
  摘要小于 600 字，保留编号与 POI，使后端当前的截断策略不会首先丢掉地点指代信息。
- 明确表达的预算、步行上限、数字每日时长、完整日期、时刻、目的城市修改可同步到 constraints；
  支持取消部分上限。仅处理确定性表达，不将这套规则宣称为任意自然语言理解。
- “第二个不要/换掉第二个”在可确定的讨论对象上解析 POI，并更新 avoid，解除相冲突的同一必去点。
  数量表达、否定修改和多对象歧义不盲目当成单个地点操作。
- 已知地址、开放时间、建议停留时长、预算的明确事实问答可直接回答，不启动规划任务；
  缺失事实明确标为未核实，不编造推荐理由、实时状态或新的工具结果。
- 供应商失败时用户原话仍被保存，重试不重复写入；后端方案若未确认本轮显式约束，前端不静默接受。
- 不新增 wire 字段，客户端 bookkeeping 用 transient，现有严格 JSON schema 保持兼容。
  不重新显示具体走法或导航步骤。

兼容说明：现阶段 currentRoute 在候选讨论时承载“本轮优化基准”，并非宣称已写入服务器。
长期应通过版本化契约明确区分 actualRoute、activeProposal、selectedBase；不要继续靠 history 文案区分状态。

## 后端必须补齐的能力

参考已核查的后端提交：`5447b9cf84319815089a6bf2b7e8b07cee2d7d03`。

1. 会话状态机：保存已确认条件、未决问题、候选版本、已应用版本和用户最新修改；
   意图区分补充条件、局部修改、解释/咨询、确认/拒绝、重新规划，不能所有输入都走 planRouteV2。
2. 模型输入：按真实角色组织消息，采用显式状态摘要和近期消息，不把完整历史递归拼进一条 user message。
   旧消息中的重置、排除或“替换”关键词不能再次被当作本轮指令执行。
3. 约束补丁：先从本轮语义产生可验证的 patch，支持新增、修改、撤销；最新明确要求优先。
   ConstraintDefaults 只补默认值，不能充当“本轮更新后的约束”的语义解析器。
4. 工具编排：把地点搜索、精确 POI、详情和交通工具真正暴露给调度器；
   必去点应先精确检索并强制进入候选池，不能只在最终结果缺点时要求用户放宽。
5. 增量修改：基于明确的候选版本定位目标，仅重算受影响的交通和时间；未要求改动的条件与地点应保留。
   “只保留一个场馆”必须允许单地点规划，不应被旧流程至少两个候选的条件强制改写。
6. 校验修订循环：将冲突和工具反馈交回调度器，在有限次数/时长内尝试修复；
   只有真实需要用户取舍时才追问，不把原始校验错误列表直接当作会话回答。
7. 返回自然回复与结构化状态分离：解释“理解了什么、本轮改了什么、还有什么不确定”，
   方案节点、约束、改动清单和工具证据另行返回；避免前端靠固定模板伪装对话。

## 联调与验收

- 同会话：预算修改、撤销避开条件、只改一个地点、指代上一版第二项、先咨询后修改、
  追问后继续、手工改点后继续、失败后重试、退出再恢复。
- 每步检查：message 只含本轮原话；候选与已应用路线不混淆；最新约束不回滚；
  未授权不自动应用/同步 POI/保存/发布；无具体导航输出。
- 验收应比较基准方案与修改后的差异及条件命中率，不能只看 HTTP 202 或工具阶段是否出现。
