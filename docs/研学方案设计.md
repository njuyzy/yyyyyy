# 从路线规划到研学方案发布

## 设计目标

用户完成路线后，能够继续完成研学设计，清楚知道何时可以发布。产品围绕“研究什么、现场怎么探究、最终产出什么”组织内容；地点、交通和费用作为执行信息。

本文件是产品与交互方案，不代表发布功能已经实现。

## 当前代码事实

- `routeDesign.java` 仅加载布局，没有路线生成、确认或发布事件处理。
- `user_fragment_route_design.xml` 有默认隐藏的路线概览和“确认此路线”按钮，没有发布按钮。
- `Route.java` 目前只保存景点名称列表，无法承载研学目标、任务和成果。
- 因此，当前仓库不足以复现所反馈的“规划好后发布按钮灰色”问题；下述状态规则是拟定设计，不能视为对现有禁用原因的确认。

## 一、主流程

学习需求 → 规划研学路线 → 完善探究任务 → 预览并发布 → 完成任务与成果复盘。

1. **学习需求**：输入研学主题、适用学段和学习目标；提供“自然生态、历史人文、科技工程”等可编辑模板。自由输入提示改为“例如：为初中生设计一次以河流水质观察为主题的研学”。
2. **规划研学路线**：每个站点展示与主题的关联、学习任务和活动时长。推荐理由说明该地点能支持什么学习目标。
3. **完善探究任务**：编辑问题、活动和成果。自动生成的内容均为建议，需用户确认；不虚构场馆开放信息、导师资质或课程认证。
4. **预览并发布**：先展示参与者将看到的完整研学方案，再提交发布。发布成功后进入方案详情，显示状态及下一步操作。
5. **成果复盘**：后续版本支持任务记录、成果提交与导师反馈，让研学不止于出行安排。

## 二、路线完成后的页面

页面标题：**研学方案设计**。

页面从上到下：

| 区域 | 展示内容 | 可操作项 |
| --- | --- | --- |
| 进度提示 | 路线已完成 · 待完善研学内容 | 查看待完善项 |
| 研学概况 | 主题、学段、学习目标、预期成果 | 编辑概况 |
| 站点任务 | 地点、探究问题、实践活动、记录成果、活动时长 | 编辑任务、调整顺序 |
| 执行安排 | 日期、集合点、人数、带队联系人、安全安排 | 编辑安排 |
| 发布检查 | 按字段列出缺失项和修改入口 | 定位并聚焦相应输入框 |
| 固定底部操作 | 保存草稿；继续完善／预览并发布 | 随状态切换主操作 |

主视觉突出主题、学习目标、任务数和成果形式。距离、车程、费用保留为次级信息。任务数量和时长仅作概览，不用作学习质量评分。

站点卡片示例（示意，地点与活动条件需核实）：

> **第 1 站 · 河流观察点**  
> 探究问题：不同位置的河水透明度是否存在差异？  
> 实践活动：在带队人员指导下，从安全岸边开展观察，使用统一方法记录并比较数据。  
> 学习成果：一张对照记录表，以及一条有证据支持的解释。  
> 活动时长：40 分钟。

## 三、解决“按钮灰色却不知道原因”

采用“有明确下一步的主按钮”，不以长期置灰承担表单校验。

| 状态 | 主按钮 | 页面反馈 |
| --- | --- | --- |
| 路线未完成 | 继续规划路线 | 展示路线缺失项 |
| 路线完成、研学字段缺失 | 完善研学内容（剩余 N 项） | 点击定位首个缺失字段，并显示全部缺失项 |
| 研学内容完成、执行字段缺失 | 完善活动安排（剩余 N 项） | 点击定位缺失字段 |
| 全部必填项通过 | 预览并发布 | 进入预览页，用户确认后提交 |
| 正在提交 | 正在发布… | 仅此阶段禁用重复提交，显示加载状态 |
| 提交失败 | 重试发布 | 保留输入，说明失败原因，允许保存草稿 |
| 发布成功 | 查看研学方案 | 展示已发布状态和详情入口 |

N 按独立的缺失字段计算，与检查清单一致；例如某站点缺少问题和成果记为两项。编辑后立即重新计算。校验状态由同一份表单数据派生，客户端和服务端采用一致规则。

状态转换不能直接等同于发布成功：点击确认路线只完成路线阶段；服务端返回成功后才能显示“已发布”。若暂时没有发布服务，只能显示“草稿已保存”。

## 四、最小发布条件

### 研学内容

- 方案标题、研学主题、适用学段。
- 至少一条可观察或可检验的学习目标，例如“能依据观察记录比较两处水体特征”。
- 至少一个站点，每站包含地点、探究问题、实践活动、活动时长和成果要求。
- 一项整体成果及基本完成标准，例如“小组提交观察报告，包含记录、比较和结论”。

### 执行安排

- 活动日期、集合地点、人数上限。
- 带队联系人及有效联系方式；公开详情不直接暴露私人联系方式。
- 与活动相符的安全安排、应急联系说明。

交通方式、费用说明等可按业务需要补充；不把封面、宣传文案或装饰性标签作为发布阻断条件。更完整的师资审核、报名与监护人流程需另行设计，不在本次最小版本中宣称已具备。

## 五、让研学定位贯穿详情和发现页

详情页顺序调整为：**研究主题 → 学习目标 → 站点任务 → 成果与评价 → 行程和报名信息**。

列表卡片优先展示“适用学段 / 探究主题 / 任务概览 / 成果形式”，筛选维度加入学段和主题。用户加入前即可判断要学习什么，而不是只看到目的地、风景图片和价格。

文案建议：“智能路线设计”改为“研学方案设计”，“确认此路线”改为“确认路线，完善研学任务”，“可选团队”改为“研学活动”。更名需与实际功能同步，不能只换文案。

## 六、开发落点与顺序

1. **先打通流程**：在 `routeDesign` 中实现表单状态、确认路线事件、缺失项定位和草稿恢复。建立共享校验结果，驱动按钮及检查清单，避免多处手动设置按钮状态。
2. **补齐数据**：引入 `StudyPlan`（主题、学段、目标、成果、执行安排、状态）和 `StudyStop`（地点、问题、活动、时长、成果）；原路线作为方案的一部分。已有路线保留，缺少研学信息时标记为待完善草稿。
3. **接入发布**：提供预览及发布接口，服务端重新校验，处理重复提交、超时和重试；发布失败不清空表单。
4. **强化呈现**：同步调整活动列表和详情，随后再加入任务记录、成果提交和反馈。

当前 `app/build.gradle.kts` 含未解决的合并冲突标记。实现与编译验证前需先解决该构建阻塞，本方案不修改构建文件。

## 七、验收场景

- 只有路线时，显示“路线已完成”及具体缺失项，主按钮可进入补全流程。
- 补完或删除任意必填项，清单、剩余数量与按钮即时一致。
- 多站点中某一站缺少任务时，能定位到对应站点字段。
- 所有必填项完成后，能预览真实内容并发起发布。
- 重复点击、网络失败和服务端校验失败均不丢失内容，也不误报发布成功。
- 离开再返回页面，以及重建页面后，草稿内容恢复且重新校验。
- 参与者在详情首屏即可看到学段、学习目标和成果形式，并可继续查看各站探究任务。
